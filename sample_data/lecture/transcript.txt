So how long does a lookup take? It depends on how long the chains are. And that brings us to probably the most important number in this whole lecture, which is the load factor. The load factor, usually written alpha, is the number of items stored divided by the number of buckets. So n over m. If I have 50 items in 100 buckets, alpha is 0.5. If I have 200 items in 100 buckets, alpha is 2 — and with chaining that's allowed, you just have longer chains.

If your hash function spreads keys out uniformly, the average chain length is alpha. So a lookup costs, on average, the time to compute the hash plus the time to walk a chain of length about alpha. We write that as O(1 + alpha). And as long as we keep alpha bounded by a constant — that's the whole game — the expected cost is O(1).

Okay. The second family is called open addressing. In open addressing, there are no chains. Every item lives directly in the array itself, one item per slot. So when you get a collision, you have to find some other slot in the array. The simplest strategy is called linear probing: if the slot you hashed to is taken, try the next one. If that's taken, try the next one. Wrap around at the end. Keep going until you find an empty slot.

So, insert: hash to slot i. Full? Try i plus 1. Full? Try i plus 2. And so on, all mod m. And lookup does the same walk: start at slot i and keep stepping forward until you either find the key, or you hit an empty slot. If you hit an empty slot, the key isn't there, because if it were, insert would have put it in that empty slot or earlier.

Let's do a tiny example. Table of size 8, slots 0 through 7. Say "fig" hashes to 5, so it goes in slot 5. "Lime" hashes to 5 too — collision — so it probes to 6. "Date" hashes to 6, which is now taken by lime, so date goes to 7. And then "pear" hashes to 7, which is taken, so it wraps around to slot 0. Look at what happened: pear and date never collided with fig directly, but they all got pulled into the same run of filled slots.

So, two consequences. First, with open addressing the load factor can never be more than 1. You only have m slots. And in practice you want to stay well below 1, because — second consequence — linear probing creates clusters. Once you have a run of filled slots, any key that hashes anywhere into that run gets added to the end of it, which makes the run longer, which makes it more likely to catch the next key. It's like a traffic jam on the highway. This is called primary clustering.

And the cost grows fast as the table fills. There's a classic textbook analysis of this: with linear probing, an unsuccessful search takes about one-half times, one plus one over one-minus-alpha squared, probes. You don't need to memorize that formula. But plug in some numbers: at half full, that's about two and a half probes. At 90 percent full, it's about 50. That's the cliff. So linear probing tables usually resize somewhere around half to two-thirds full.

There are other probing strategies — quadratic probing, where you jump by 1, then 4, then 9, and so on, and double hashing, where a second hash function decides the step size. They both reduce clustering. But linear probing has a big practical advantage: it walks through memory in order, which is really friendly to your CPU cache. Okay. Let's talk about resizing, because that's how we keep alpha small.

The idea: when the load factor crosses some threshold, allocate a new, bigger array — usually twice as big — and move everything over. Now here's the part people get wrong. You cannot just copy the items into the same positions in the new array. Remember, the index is the hash of k mod m. When m changes, the index changes. So every key has to be rehashed and reinserted into the new table. That's why it's called rehashing.

So a single resize is expensive. It's O(n), because you touch every item. And that sounds bad. If an insert can cost O(n), how can we claim inserts are O(1)?

The answer is amortized analysis, which you saw on problem set four with dynamic arrays. Same argument. If you double the table each time, the resizes happen at sizes 1, 2, 4, 8, and so on, up to n. The total copying work is 1 plus 2 plus 4 plus up to n, which is less than 2n. Spread that over n inserts, and each insert pays a constant amount extra. So any one insert might be slow, but the average cost per insert, over any sequence of inserts, is O(1). That's what amortized O(1) means. It's a guarantee about the total, not about each individual operation.

And notice it matters that we double, rather than add a fixed number of slots. If you grow by, say, a hundred slots each time, you resize every hundred inserts, and the total copying work becomes quadratic. Growing geometrically is what makes the math work.

Okay, so, let's make this concrete with something you use every day: the Python dictionary. A Python dict is a hash table. When you write d, bracket, "riley," bracket, equals 3, Python calls hash on the string "riley," uses some of the bits of that hash to pick a slot, and stores the key and value there.

A few things about Python's dict that I think are fun. First, it uses open addressing, not chaining. It doesn't use plain linear probing, though — it uses a probe sequence that gradually mixes in the higher bits of the hash, so that keys that collide once don't keep colliding forever. Second, the table size is always a power of two, so instead of computing mod m, it can just grab the low bits of the hash, which is very fast. And fourth, since Python 3.7, dictionaries are guaranteed to remember insertion order. That's done with a separate compact array of entries, and the hash table itself just stores small indexes into that array.

Also, only hashable things can be keys. Strings, numbers, tuples of hashable things — fine. But if you try to use a list as a dictionary key, you get a TypeError: unhashable type: 'list'. And that's not Python being fussy. Think about it: if you could put a list in as a key and then append to it, its hash would change, and it'd be sitting in the wrong bucket forever. Mutable keys break the "equal keys, equal hashes, every time" rule.

Little bit of trivia, since we're here. Try hash of 42 in Python. You get 42. Small integers hash to themselves. Now try hash of negative 1. You get negative 2. And the reason is — this is a great piece of C history — inside CPython, a hash function returns negative 1 to signal an error, so a real hash of negative 1 had to be bumped to negative 2. Nobody needs to know that. But now you do.

Okay, so, the security thing I promised. Remember: the worst case is every key in one bucket, O(n) per operation. If an attacker knows your hash function, they can craft thousands of keys that all collide — say, as the parameter names in a web request — and your server's dictionary turns into a linked list, and processing one request takes quadratic time. This is called a hash flooding attack, and around 2011 it was shown to work against a bunch of popular web frameworks. The fix in Python: string hashes are salted with a random seed each time the interpreter starts. That's why, if you print the hash of a string in two different Python sessions, you'll get two different numbers. Your program shouldn't depend on those values anyway. The rule is still same key in, same hash out — within one run.

Hash tables are everywhere in systems, and two patterns you'll see over and over are deduplication and caching.

Deduplication: say you've got a log with ten million events and you want to know how many distinct users showed up. The naive approach compares every event against every other event — that's O(n squared), and with ten million events you will be waiting a very long time. Instead, you keep a set — which in Python is also a hash table, just keys with no values — and for each event you ask "have I seen this user before?" That's an O(1) check on average, so the whole thing is O(n). One pass through the log.

Caching: suppose you have a function that's expensive — it calls a slow web API, or it recomputes some big feature for a model. You keep a dictionary from inputs to outputs. Before doing the expensive work, you check the dictionary. If the answer's already there, return it. That's memoization, and Python's functools.lru_cache decorator does it for you with a dictionary under the hood. Your web browser does the same thing with pages and images, keyed by URL. One: a hash function turns a key into an integer, and mod m turns that into a bucket index. Good hash functions are deterministic, uniform, and fast.
